# ServisZeka — katkıda bulunanlar için notlar

AI-native ITIL 4 hizmet yönetimi platformu. Python 3.11+, FastAPI, SQLAlchemy 2 (async), pydantic v2. Kaynak kod `src/serviszeka/` altında (src layout).

## Komutlar

```bash
uv sync                  # bağımlılıklar
uv run pytest            # testler (asyncio_mode=auto, bellek içi SQLite)
uv run ruff check .      # lint
uv run uvicorn serviszeka.main:app --reload   # yerel sunucu
uv run alembic upgrade head                   # göçleri uygula (üretimde şema böyle kurulur)
uv run alembic check                          # modeller ile göçler arasında fark yok mu
uv run alembic revision --autogenerate -m "..."   # model değişince yeni göç
uv run python evals/run_eval.py --oracle          # değerlendirme boru hattı duman testi
uv run python evals/run_eval.py                   # gerçek LLM ile %70 kapısı (SZ_ANTHROPIC_API_KEY gerekir)
uv run python evals/run_request_eval.py           # Faz 3 kapısı (küçük senaryo): standart taleplerin %50'si insansız (sahte dizin, ağ yok)
uv run python evals/run_automation_eval.py        # Faz 3 kapısı (etiketli 200 talep): oran >= %50 VE yanlış insansız = 0 (LLM'siz, ağ yok)
```

Web portalı (`portal/`, Vite + React + TS; ayrıntı ve ekran sahipliği `portal/README.md`):

```bash
cd portal && npm ci
npm run typecheck && npm run lint && npm test -- --run && npm run build
npm run format:check      # Prettier
npm run e2e               # Playwright E2E (olay, bilgi bankası, yalıtım, Faz 2 değişiklik/CAB/standart/yetki; Faz 3 `faz3-*.spec.ts`: katalog/insansız, R3 iki onay, sorun/RCA): API'yi (geçici SQLite, dev kimlik, SZ_LLM_PROVIDER=fake) ve Vite'ı kendisi başlatır — Faz 1/2 gölge mod açık (8765/5180), Faz 3 ayrı çift gölge mod kapalı + sahte dizin (8766/5181, `E2E_PROFILE=faz3`)
npm run sync:api          # backend OpenAPI -> portal/openapi.json -> src/api/schema.d.ts + taxonomy.json kopyası
docker build -t serviszeka-portal portal   # nginx imajı (SPA geri dönüşü, sıkı CSP)
```

Yerel deneme (API anahtarsız triage): `SZ_ENVIRONMENT=development SZ_AUTH_MODE=dev SZ_LLM_PROVIDER=fake SZ_CORS_ORIGINS=http://localhost:5173 uv run uvicorn serviszeka.main:app --reload`, ardından `cd portal && npm run dev`.

## Mimari kurallar

- **Her yapay zekâ eylemi** önce `serviszeka.policy.evaluate(...)` ile değerlendirilmeli, sonucu bir `AIDecision` kaydı olarak saklanmalı ve `serviszeka.audit.record(...)` ile denetim zincirine yazılmalıdır. Politikayı atlayan ajan kodu kabul edilmez.
- Gölge mod (`SZ_AI_SHADOW_MODE=true`) açıkken ajanlar yalnızca önerir, uygulamaz.
- **LLM çağrıları yalnızca `serviszeka.llm`** üzerinden yapılır (PII'yi `privacy.mask_pii` ile maskeler). `anthropic` SDK'sını doğrudan çağırmayın.
- `audit.record` commit etmez; commit işlemi çağıran servis/endpoint'in sorumluluğundadır.
- **Gizli bilgileri asla koda yazmayın**; tüm ayarlar `SZ_` önekli ortam değişkenlerinden `config.get_settings()` ile okunur (bkz. `.env.example`).
- Testlerde gerçek dış servis çağrılmaz: `FakeLLM` ve `httpx.MockTransport` kullanın. `SZ_LLM_PROVIDER=fake` (`llm/fake.py`, deterministik anahtar kelime sınıflandırması + değişiklik risk anlatısı; yeni bir ajan istemi eklerseniz fake yanıtını da ekleyin, yoksa karar `escalated` düşer) yalnızca geliştirme/E2E içindir; `SZ_ENVIRONMENT=development` dışında açılış reddedilir.
- **Şema değişikliği = göç**: `models.py` değişince `migrations/versions/` altına Alembic göçü ekleyin; `alembic check` temiz kalmalı. `create_all` yalnızca geliştirme/test içindir (`SZ_AUTO_CREATE_SCHEMA`, varsayılan true); üretimde `SZ_AUTO_CREATE_SCHEMA=false` ve `alembic upgrade head`.
- Sınıflandırma değerleri (`category`, `service`, `assignment_group`) yalnızca `src/serviszeka/taxonomy.json` listesinden gelir; liste değişirse `evals/data/dataset.jsonl` etiketleri ve portal kopyası (`cd portal && npm run gen:taxonomy`; kısa adlar `portal/src/lib/taxonomy.ts`) güncellenmelidir.
- **Kimlik doğrulama**: `GET /health` ve belgeler dışındaki her uç nokta `serviszeka.auth` ile korunur. Yeni yönlendirici `APIRouter(..., dependencies=[Depends(get_current_user)])` ile kurulmalı, her uç nokta rolünü `AgentUser` / `ReaderUser` / `ApproverUser` / `AdminUser` / `CreatorUser` / `IncidentViewerUser`, Faz 2'de `ChangeViewerUser` / `ChangeCreatorUser` / `ChangeManagerUser` / `CabUser` / `CMDBReaderUser` / `CMDBWriterUser`, Faz 3'te `ActionApproverUser` ve sorun yönetiminde `api.problems.ProblemUser` (agent/approver) (veya `require_roles(...)`) ile istemelidir. `requester` ve yalnızca `approver` değişiklik/CMDB uçlarını göremez (403). `requester` (self-servis) rolü yalnızca kendi kayıtlarını (caller == kullanıcı) görür; `user.is_requester_only` ise süzün, başkasının kaydına `404` dönün ve yapay zekâ iç ayrıntılarını (kararlar, `ai_confidence`) göstermeyin. Başkası adına kayıt (`caller`, `impact`) yalnızca agent/admin açar; agent olmayan her kullanıcıda (requester+approver dahil) `caller` belirteçteki kullanıcıdır. Aktör/onaylayan yalnızca `user.username`'den gelir; `X-Actor` gibi istemci başlıklarına güvenmeyin. `tests/test_auth.py::test_every_api_route_requires_auth` korumasız uç noktayı yakalar; OpenAPI dışındaki `/mcp` kendi bearer doğrulamasını yapar (`tests/test_mcp.py`).
- Varsayılanlar güvenlidir: `SZ_ENVIRONMENT=production`, `SZ_AUTH_MODE=oidc` (`SZ_AUTH_ISSUER` + `SZ_AUTH_AUDIENCE` zorunlu). `SZ_AUTH_MODE=dev` (`Bearer dev:<kullanıcı>:<roller>`, imza doğrulamasız) yalnızca `SZ_ENVIRONMENT=development` iken çalışır; aksi halde uygulama açılmaz.
- Testler `tests/conftest.py` içindeki autouse fikstürle dev kipinde çalışır; API testleri `tests/_auth.py` (`AGENT`, `APPROVER`, `ADMIN`, `dev_headers`) başlıklarını kullanır. OIDC yolu `tests/test_auth.py`'de testte üretilen RSA/EC anahtarları ve `httpx.MockTransport` JWKS ile sınanır.
- API sözleşmesi değişince `cd portal && npm run sync:api` çalıştırın (OpenAPI dışa aktarımı + portal tipleri + taksonomi kopyası); CI fark bulursa kırılır.
- Portal: ekranlar ham enum/taksonomi anahtarı göstermez (`@/lib/labels`, `@/lib/fields`, `@/lib/taxonomy`); sorgu anahtarları yalnızca `@/api/queryKeys`'ten; sunucu/yapay zekâ metni düz metin (dangerouslySetInnerHTML yasak); belirteç localStorage'a yazılmaz.
- **Faz 2 kapısı — hiçbir riskli eylem onaysız çalışmaz** (`tests/test_gate_no_unapproved_risk.py`, `tests/test_gate_review_regressions.py`, `tests/test_changes.py::test_gate_*`, E2E `portal/e2e/change-flow|standard-change`). Değişiklik durum geçişleri ve CAB/ECAB onayları yalnızca insan aktörle (`ai:` önekli aktör reddedilir) `services.changes.transition` / `record_approval` üzerinden yapılır; ajanlar bunları çağıramaz (statik tarama yakalar). Ajanlar yalnızca risk alanlarını, `policy.evaluate` `auto_applied` derse ve riski yükseltiyorsa yazar; düşürme change_manager onayı ister. `change.execute`/`change.approve` politikada asla otomatik değildir. Talep eden ve uygulayıcı kendi değişikliğine oy veremez (kimlikler `services.changes.same_identity` ile büyük/küçük harfe duyarsız karşılaştırılır); zamanlama/uygulama anında onaylar, standart uygunluk (risk CMDB'den yeniden hesaplanır, CI'sız standart CAB'a gider) ve çakışmalar (etkilenen CI satırları kilitlenerek) yeniden denetlenir. Etki analizi `cmdb.MAX_IMPACT_NODES` ile sınırlıdır; kesilen analiz (`truncated`) riskte en kötü durum sayılır. Değişiklik kararları olay karar kutusunda (`/incidents/decisions`) görünmez. Yeni bir riskli eylem eklerken önce bu kapıya başarısız bir test ekleyin.
- **Faz 3 — araçlar ve MCP** (`docs/faz3.md`; kapı `tests/test_gate_no_unapproved_risk.py` bölüm 4, `tests/test_tools.py`, `tests/test_actions.py`, `tests/test_mcp.py`). Yeni otomasyon yeteneği `serviszeka.tools` altında bir `ToolSpec` (ad `alan.fiil_nesne`, Türkçe açıklama, R0-R3 risk sınıfı, gerekirse `risk_fn` ile koşullu risk — temel sınıfın altına inemez —, pydantic argüman modeli `extra="forbid"`, insan rolleri, bağlayıcılar) olarak eklenir ve `policy.POLICIES`'e `(alan, fiil)` girdisi alır (R1 en fazla LOW, R2/R3 `None`). İşleyici mevcut servisi `ctx.actor` ile çağırır (iş kuralını kopyalamaz), commit etmez; işleyiciye yalnızca `tools.execute_tool` ve `tools.actions` ulaşır (statik tarama). Sorun yönetimi ajanı (`agents/problem.py`) yalnızca `execute_tool` ile `ai:problem` olarak yazar; sorunu çözemez/kapatamaz, kesin RCA yazamaz (yalnızca `rca_draft`), geçici çözüm yayımı ve kapatma R2 (kapı bölüm 5). R2/R3 asla doğrudan çalışmaz: `ActionRequest` açılır, insan onayıyla (yapay zekâ ve talep eden onaylayamaz, R3 iki kişi ya da CAB onaylı değişiklik, süre aşımı) onaylayanın kimliğiyle yürütülür; yürütmede argüman ve risk yeniden denetlenir. `ai_agent` rolü her zaman `ai:<istemci>` aktörüne ve yalnızca `ai_agent` rolüne indirgenir (`auth.principal`). Yapay zekâya dönen araç sonucu PII maskelidir. Dış sistemler (Entra ID / Graph / Teams; Keycloak / Slack) yalnızca `tools.connectors` arayüzleri arkasından, `httpx` + testte `MockTransport` ile. Hizmet talepleri (`services/requests.py`): iş onayı risk onayından önce gelir ve yapay zekâ/talep eden/açan veremez; karşılama adımları yalnızca `execute_tool` ile `ai:fulfilment` olarak çalışır; insansız (`touchless`) yalnızca sıfır insan onayı ve sıfır insan düzenlemesiyle `fulfilled` talep (kapı bölüm 6, `tests/test_requests.py`). Geçici parola hiçbir sonuç/denetim/istekte yer almaz.
- **Yeni araç = risk sınıfı + kapı testi** (aynı değişiklikte, önce başarısız test): (1) `ToolSpec` `tools.registry`'ye kayıtlı ve R0-R3 sınıfı var, `policy.POLICIES`'te `(alan, fiil)` girdisi var (`test_gate_tools_every_tool_has_risk_class_and_policy`); (2) R2/R3 araç için `tests/test_gate_no_unapproved_risk.py` `RISKY_SAMPLES`'a geçerli örnek argüman (`test_gate_tools_every_risky_tool_has_a_sample` aksi halde kırılır; en gevşek politikada yapay zekâ çağrısı hiçbir şey yazmamalı); (3) `risk_fn` varsa riskin yükseldiği durum `CONDITIONAL_RISKY` / `IDENTITY_CONDITIONAL`'a; (4) R0/R1 işleyici `tests/test_tools.py::test_every_r0_r1_handler_runs_against_services` örneğine; (5) araç bir katalog adımı olabiliyorsa `evals/data/requests.jsonl`'a (üretici `evals/generate_requests_dataset.py`) otomatikleşmesi ve otomatikleşmemesi gereken etiketli satırlar eklenir ve `evals/run_automation_eval.py` yanlış insansız 0 ile geçmelidir. Hesaba/erişime dokunan R1 araç başkası adına / talepsiz / devre dışı hesapta R2'ye çıkmalıdır (`identity.reset_password`, `identity.unlock_account` örneği: `services.requests.verify_self_service`). Kapı testleri yalnızca genişletilir, gevşetilmez.
